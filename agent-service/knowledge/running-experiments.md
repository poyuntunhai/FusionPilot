## 标准实验流程 experiment workflow

一次规范的实验按四步走：先读当前工作配置、知道起点；再改要变的字段；然后校验或直接运行；最后
只引用运行返回的指标做解释。

每一步的结论都要能追溯到结构化结果：数值只能来自仿真核心的返回，不能由语言模型回忆或推算。
配置字段一次只改需要变的那几个，没提到的字段沿用当前工作配置。

## 修改配置 update config

改配置时只提交要变的字段，例如只想改目标数就只写 `targetCount`。

改完之后核心会全量校验整份配置，不合法就整体拒绝、不写入会话，所以不需要先单独校验一次。
如果被拒绝，错误信息里会说明是哪个字段不合法，按提示改即可。配置字段名必须用 camelCase 原名。

## 运行与确认 confirmation gate

运行仿真是一个"会花资源且会产生结论"的动作，默认需要用户明确确认后才会执行；确认前，待执行的
调用会以一张确认卡片展示，说明这次运行要验证什么。

用户批准后才会真正跑。用户可以拒绝，被拒绝的调用不会执行，会话继续等下一步指令。一次对比实验
（轮询 vs 优先级）同样是**一次**确认，平台会在同一份配置下连跑两次并给出两侧指标和差值。

## 运行记录与复现 run history reproduce

每次运行都会在平台上留下一条记录，带自己的运行 id、配置摘要和完成时间，可以在工作台里重新打开、
查看轨迹和导出。

同一个配置和种子重复运行会得到相同指标，这是确定性复现；两条运行记录仍然是两条独立的记录，
各自带自己的运行 id。用户说"上次那次"时，指的是某条具体运行记录，而不是某个被缓存的数值。

## 一次改一个变量 one variable at a time

要比较两个方案，就只让被比较的那个字段不同：比较融合方法只改 `fusionMethod`，比较调度策略只改
`schedulingPolicy`，其他字段、`randomSeed` 和 `simulationSteps` 保持一致。

同时改两个字段会得到无法归因的差异。另外要检查配置是否真的能产生差异：`availableResources` 大于
等于 `targetCount` 时两种调度策略结果相同，目标噪声为 0 时几种融合方法的结果也会趋同。

## 多步实验与探索性目标 multi-step exploration

当一个目标需要跑多次才能回答（对比两种方法、看某个参数从 2 变到 4 的影响、做敏感性分析）时，
先规划出一个多步序列再执行更合适：序列里每一步是什么、先改什么后跑什么，都在开始前一次性列清，
用户确认整批后连续执行。

这样避免"跑一次、看一眼、再决定跑什么"的来回确认，也让实验的推理链条在开始前就是可见、可检查的。
单个动作（只改一个参数、只跑一次、只读一次结果）不需要规划，直接执行即可。
