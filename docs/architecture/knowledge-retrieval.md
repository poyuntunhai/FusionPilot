# FusionPilot Knowledge Retrieval（领域知识检索）

本文记录 Agent 的领域知识检索层：为什么需要它、语料长什么样、检索怎么工作，以及**为什么这一层
不需要向量数据库**，以及什么条件下才需要改。

这是一份设计契约，不是能力宣传。

## 为什么需要检索

概念类问题如果交给模型凭先验回答，在这个平台上会**稳定地答错**，而且错得看不出来。原因是平台有若干
与教科书不同的既有事实：

- 融合层能直接拿到目标真值状态，因此除 `KALMAN_FILTER` 外的四种方法上报的速度不是估计量；
- 指标是单个随机种子上的均值，也就是一个样本，不能据此给方法排序；
- 卡尔曼滤波的过程噪声是一个按"不机动"整定的假设值，不是标定值；
- 关联与门限参考的是上一步的融合估计外推，不是真值。

这些都是平台自身的设计选择，任何通用模型都不可能知道。检索的作用就是把回答限制在"从 Java 核心
整理出来的文字"里，并在回答上标出用到了哪几节，让读者能自己核对。

## 语料

位置：`agent-service/knowledge/*.md`（可用环境变量 `KNOWLEDGE_DIR` 指向别处）。当前 7 个文档、
42 个小节：

| 文档 | 内容 |
|---|---|
| `fusion-methods.md` | 五种融合方法各自做了什么、上报什么、什么场景用 |
| `scheduling-policies.md` | 两种调度策略、为什么资源充足时对比没有意义 |
| `metrics.md` | 五个聚合指标的准确定义、逐步指标、怎么组合读 |
| `experiment-config.md` | 配置字段、合法取值范围、违反时的行为 |
| `observation-model.md` | 真值生成、观测生成、观测源类型、时延、能力边界 |
| `platform-limitations.md` | 确定性复现（不是缓存）、单种子单样本、已知简化假设 |
| `running-experiments.md` | 平台上的实验流程、确认门、运行记录、一次改一个变量 |

格式：文件开头的 `---` 块给出 `doc` 与 `tags`，此后**每个 `## 小节` 是一个检索单元**。

```markdown
---
doc: fusion-methods
title: 多源数据融合方法
tags: 融合方法, fusionMethod, fusion, 算法
---

## 卡尔曼滤波 KALMAN_FILTER kalman filter

为每个目标维护一个匀速卡尔曼滤波器……
```

约定两条：

- **小节标题要带上英文别名**。标题同时参与检索和展示（展示时会自动去掉尾部的英文部分），
  `KALMAN_FILTER`、`trackingRate` 这类枚举名放在标题里，英文提问才能命中。
- **一个小节只回答一件事**。粒度就是检索质量：`## 资源利用率` 和 `## 平均位置误差` 分开写，
  问其中一个才不会把另一个一起拖进来。

语料的权威来源是 Java 核心与 `memory-bank` 中的领域参考；如果代码与语料冲突，**以代码为准，
并把语料改过来**。

## 检索怎么工作

`app/knowledge.py`，纯标准库，无第三方依赖：

1. **分词**（`tokenize`）。ASCII 保留 `snake_case` 整体（`weighted_average` 是枚举值，必须整体匹配），
   同时贡献它的组成部分，这样"平均误差"这样的问法也能命中只出现过枚举名的小节。中文走
   **领域词典 + 字符二元组**：先在 `LEXICON` 里做最长匹配，再补上所有相邻二字组。这样"卡尔曼滤波"
   这种词靠词典精确命中，词典外的词（性能、部署）靠二元组兜底。功能词（什么、怎么、请问、区别）
   进停用词表——它们每句话都有，留着只会让不相关的问题看起来相似。
2. **同义词扩展**（`SYNONYMS`）。把用户的说法映射到语料的说法："定位精度"→`averagePositionError`、
   "缓存"→`determinism`、"轮询"→`round_robin`。这是问题措辞与语料措辞之间的唯一接口，扩展只做
   一层，不做传递闭包，避免一次查询把半个语言都拉进来。
3. **打分**。BM25（k1=1.5, b=0.75），外加两档加权：命中**小节标题**权重 ×2.4，命中**文档 tags**
   ×1.6。分开加权是有意的——标题里的词是这个节"关于什么"，正文里的同一个词经常只是顺带提到；
   不加这个区分，"怎么读这些指标"这种泛泛的小节会凭词频压过具体的指标小节。
4. **截断**。先按分数排序，再丢掉低于最高分 25% 的结果，最后取 `limit`（默认 3）条。相对阈值是
   为了不让一个强命中带上四条勉强相关的尾巴。返回空列表是**正常结果**：它就是"平台资料里没有
   这一节"的信号，调用方据此拒答而不是硬答。

一次查询是微秒级、确定性、零成本。

## 为什么不用向量数据库

**当前规模下引入向量库是负收益。** 具体理由：

1. **语料只有几十个小节。** 向量检索解决的是"海量语料里召回语义相近但用词不同的内容"。几十个
   小节的暴力检索本来就是全量扫描，ANN 索引（HNSW/IVF）解决的是它没有的规模问题。
2. **这个领域的提问本来就用词精确。** "什么是卡尔曼滤波"、"跟踪率怎么算"、"DISTANCE_GATED 和
   加权平均的区别"——查询词几乎总能在语料里原样出现。这正是词法检索最好的区间，而语义检索在这
   里的表现往往**更差**：把"融合方法"的向量和"调度策略"的向量放在一起比，模型级的嵌入会认为
   它们高度相似（都是"雷达信号处理概念"），于是问融合却召回调度。
3. **确定性和可复现是我们自己定的硬要求。** Agent 的每个结论都要能追溯到证据；检索结果随机
   波动（换一次嵌入模型、换一次分块）会让同一句话无法复现。词法检索在任何机器、任何时候给出
   同一份结果。
4. **运维成本不对等。** 向量库意味着一个要部署、要备份、要监控、要配 key 的外部服务，
   或者至少一份要版本化的索引文件。为了几十个小节付这个代价不合理。
5. **这里没有需要它解决的东西。** 没有多模态、没有十万级文档、没有跨语言检索需求。

对应的取舍是明确承认的：**纯同义改写、完全不含领域词的提问会召回失败**。例如"怎么衡量分配得好
不好"——如果 `SYNONYMS` 没有覆盖"分配得好不好"→`resourceUtilization`，就会返回空。当前的应对
方式是把这类说法补进 `SYNONYMS`（一行映射），并把「召回为空」当作正常结果处理，而不是硬答。

## 什么时候需要重新评估

满足任一条，就值得把嵌入检索加进来（作为**混合检索的召回侧或重排侧**，不是替换）：

- 语料超过约 300 个小节，或加入大量叙述性长文（设计文档、论文笔记）；
- 评测集显示相当比例的提问是**不含领域词的同义改写**，且补同义词表已经追不上；
- 语料扩展到多来源、多语言或包含代码/表格等多模态内容；
- 需要按语义做去重或聚类。

真要加的时候**仍然不需要向量数据库**：

- 向量存成一个版本化的本地文件（`numpy`/JSON），进程内做余弦相似度即可，此时规模仍然是万级以下；
- 嵌入用**用户已有的 BYOK key**，不存在新增外部依赖；
- 接入点在 `KnowledgeIndex.search`，调用方（图节点、工具、HTTP 接口）完全不感知；
- 保险做法是保留词法 BM25 作为召回底座，只用嵌入做重排或补召回，这样"精确词命中"的能力不会丢。

**用户侧需要做的事：当前没有。** 检索层零外部依赖、零配置、零 key；`KNOWLEDGE_DIR` 不设置就用
内置语料。只有将来真的启用嵌入检索，才需要选一个支持 embeddings 的供应商（现有供应商里 OpenAI /
Qwen / Zhipu 都提供）——也仍然只是填一个 key，不需要安装或运维任何数据库。

## 接在哪里

- **`answer_concept` 节点**：检索后把材料注入 system prompt 的 `## 知识库` 段，并把来源写在
  assistant 消息的 `knowledge` 字段上（随会话快照持久化，重新打开对话仍能看到来源）。
- **`plan_experiment` 节点**：同一份材料注入 `## 参考材料` 段。规划器是最容易造成实质损害的环节
  ——一个字段取值写错会让整批步骤失败，把合法枚举名和取值范围摆在它面前是廉价且必要的约束。
- **`search_knowledge` 工具**：只读、不需要确认，供工具循环在实验回合中随时查阅（"这个滤波器估计
  速度吗"）。它被排除在 `PLANNABLE_TOOLS` 之外——一个只读资料的步骤放进待批准的计划里没有意义。
- **`GET /api/v1/agent/knowledge/search`**：直接暴露检索，供人工核对与评测使用。一个答错的回答和
  一个坏掉的索引在对话记录里长得一模一样，这个接口是用来把两者区分开的。

注入块的标题（`## 知识库` / `## 参考材料`）是**契约**：提示词里用散文提到这两样材料，但永远不会
产生这两行；mock provider 与端到端检查靠它判断"材料是否真的被检索进来了"。曾经因为用
"知识库"三个字做判据，导致每个请求都被判成"有材料"，端到端检查把这个假阳性抓了出来。

## 降级行为

- 语料目录不存在、为空、或某个文件解析失败：返回空结果，Agent 明确说"平台资料里没有这一部分"，
  不编造。
- 检索结果为空：概念回答不带引用条，`knowledge_retrieved` 事件 `grounded=false`。
- 检索层不发起任何网络调用，也不依赖模型凭证，因此**在任何模式下都不会让一个回合失败**。
