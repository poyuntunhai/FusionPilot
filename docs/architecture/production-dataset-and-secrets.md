# FusionPilot Production And Dataset Boundary

This document records the implementation boundary for a public deployment and
user-owned research data. It is a design contract, not a claim that every
planned feature is already implemented.

## Production deployment

- The public entry point will be HTTPS behind a reverse proxy such as Nginx.
- Vue is served as static assets; `/api` is proxied to Spring Boot and Agent
  endpoints are proxied to FastAPI.
- MySQL credentials, session secrets, model provider keys, and storage paths
  remain server-side environment or secret-manager values.
- The browser stores only the opaque login token required by the current local
  MVP. Production deployment should prefer secure, HttpOnly, SameSite cookies.
- User, dataset, simulation, and Agent records must be scoped by authenticated
  `user_id`. Public health checks must not expose secrets or data.
- Long-running simulations need server-side cancellation, request timeouts,
  quotas, and a job status model before public multi-user deployment.

## Model API key strategy

The default product mode is platform-managed providers: users select a provider
and model, while the site owner configures provider keys on the server. Keys are
never sent to Vue or embedded in JavaScript.

An optional BYOK mode can be added later. A user submits a key over HTTPS to a
dedicated backend endpoint; the backend validates it, encrypts it using a
deployment secret or KMS, and stores only an encrypted value or a reference.
The Agent service reads the decrypted key only for the request that needs it.
The UI displays provider, model, and validation status, never the key again.
Keys must be revocable, masked, audited, rate-limited, and deleted on request.

## Dataset contract

The current default scene is synthetic and is generated by Java. A real user
dataset is not loaded by the current `GET /api/v1/experiments/default` route.

The first import contract should be a UTF-8 ZIP containing:

- `manifest.json`: dataset version, coordinate frame, units, time convention,
  source descriptions, and schema version.
- `truth.csv` (optional for display, required for error metrics): `time_step`,
  `target_id`, `x`, `y`, optional `z`, and optional velocities.
- `observations.csv`: `time_step`, `sensor_id`, `source_type`, optional
  `target_id`, measurement values, availability, confidence, noise, and delay.
- `interference.csv` (optional): time range, affected source/resource, and
  abstract noise, missing, or delay modifiers.

The canonical runtime representation is normalized records, not a file suffix.
CSV is the first user-facing format because it is inspectable in DataGrip and
spreadsheets. JSON is useful for small nested records. Parquet can be added for
large columnar datasets. MAT, HDF5, NetCDF, and GeoJSON should be import
adapters, not the core simulation representation.

Every import must declare timestamp semantics, coordinate reference system,
axis units, and whether positions are local ENU meters or geographic
longitude/latitude. The server validates required columns, numeric values,
duplicate keys, time ordering, and ownership before creating a dataset version.

## User flow

Upload -> validate and preview -> map columns if needed -> normalize and create
a version -> build a scene from that version -> run -> replay truth,
observations, fused tracks, and scheduling results. Raw files live in
user-scoped filesystem/object storage; MySQL stores metadata, ownership,
validation summary, and queryable normalized records. Large raw blobs should
move to S3/MinIO before public scale.
