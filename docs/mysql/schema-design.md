# FusionPilot MySQL Relational Schema Design

## Goal

The current MySQL step stores each simulation run as one row with JSON snapshots.
That is useful for quick persistence, but it is not enough for backend practice,
query practice, charts, or Agent trace replay.

This design normalizes the most important data into relational tables while
keeping JSON snapshots where they are useful for reproducibility.

## Design Principles

- Java remains the source of truth for simulation logic.
- MySQL stores experiment history and queryable result details.
- FastAPI Agent should not write simulation domain tables directly.
- Vue should read Java APIs, not access MySQL.
- Every simulation run keeps a config JSON and result JSON snapshot.
- Frequently queried values are promoted into typed columns.
- Step, target, observation, fusion, scheduling, and Agent trace data are split into tables.

## Core Entity Relationship

```text
fp_simulation_run 1 --- n fp_simulation_step
fp_simulation_step 1 --- n fp_target_truth
fp_simulation_step 1 --- n fp_observation
fp_simulation_step 1 --- n fp_fused_state
fp_simulation_step 1 --- n fp_resource_assignment
fp_simulation_step 1 --- 1 fp_step_metric

fp_agent_session 1 --- n fp_agent_trace_event
fp_agent_session 1 --- n fp_agent_tool_call
```

## Tables

### fp_simulation_run

Run-level metadata and reproducibility snapshot.

Important columns:

- `run_id`: primary key generated by Java.
- `scenario_name`: scene name.
- `target_count`: configured target count.
- `simulation_steps`: configured step count.
- `scheduling_policy`: policy used by this run.
- `random_seed`: reproducibility seed.
- aggregate metric columns: useful for list pages and comparisons.
- `config_json`: exact experiment config snapshot.
- `result_json`: exact full result snapshot for compatibility.
- `completed_at`: finish time.

Why keep JSON here:

- It preserves the exact DTO returned by Java.
- It lets old API behavior keep working during migration.
- It is a useful fallback when normalized detail tables change.

### fp_simulation_step

One row per time step in a run.

Important columns:

- `step_id`: surrogate primary key.
- `run_id`: foreign key to `fp_simulation_run`.
- `time_step`: zero-based step index.

Important constraint:

- `(run_id, time_step)` should be unique.

### fp_target_truth

Ground-truth target state for one time step.

Important columns:

- `step_id`: foreign key to step.
- `target_id`: domain target id.
- `x`, `y`: true position.
- `velocity_x`, `velocity_y`: true velocity.

Typical query:

- Draw true trajectory for target 1 in one run.

### fp_observation

Raw observation from radar, EO/IR, or prior source.

Important columns:

- `source_type`: `RADAR`, `EO_IR`, or `PRIOR_KNOWLEDGE`.
- `available`: whether the observation was available.
- `x`, `y`: observed position, nullable when unavailable.
- `confidence`: source confidence.

Typical query:

- Compare observation density and missing rate by source.

### fp_fused_state

Fused estimate for a target at one step.

Important columns:

- `x`, `y`: fused position.
- `velocity_x`, `velocity_y`: fused velocity.
- `uncertainty`: uncertainty value.
- `association_confidence`: association/fusion confidence.
- `predicted_only`: whether this state is prediction-only.

Typical query:

- Compare truth and fused trajectory.

### fp_resource_assignment

Scheduling decision for one target at one step.

Important columns:

- `allocated`: whether a resource was allocated.
- `priority_rank`: rank returned by scheduler.
- `priority_score`: score used by priority scheduler.
- `reason`: explanation text.

Typical query:

- Find which targets were not served most often.

### fp_step_metric

Metrics for one time step.

Important columns:

- `average_position_error`
- `tracking_rate`
- `resource_utilization`
- `allocated_target_count`
- `unserved_target_count`

Typical query:

- Plot metric trends across time.

### fp_agent_session

Agent-level task/session record.

Important columns:

- `trace_id`: primary key from FastAPI Agent.
- `goal`: user goal.
- `status`: current session state.
- `confirmed`: user confirmation state.
- `plan_json`: structured experiment plan.

### fp_agent_trace_event

Fine-grained Agent trace events.

Important columns:

- `event_id`
- `trace_id`
- `event_type`
- `payload_json`
- `created_at`

### fp_agent_tool_call

One row per Agent tool call.

Important columns:

- `tool_call_id`
- `trace_id`
- `tool_name`
- `status`
- `input_json`
- `result_json`
- `error_message`
- `started_at`
- `completed_at`

## Index Plan

Simulation:

- `fp_simulation_run(completed_at)`
- `fp_simulation_run(scheduling_policy)`
- `fp_simulation_step(run_id, time_step)`
- `fp_target_truth(step_id, target_id)`
- `fp_observation(step_id, source_type, target_id)`
- `fp_fused_state(step_id, target_id)`
- `fp_resource_assignment(step_id, allocated, target_id)`

Agent:

- `fp_agent_session(updated_at)`
- `fp_agent_trace_event(trace_id, created_at)`
- `fp_agent_tool_call(trace_id, started_at)`
- `fp_agent_tool_call(tool_name, status)`

## Backend Learning Points

- Primary key: uniquely identifies each row.
- Foreign key: preserves parent-child relationships.
- One-to-many: one run has many steps, one step has many observations.
- Unique index: prevents duplicate step numbers in one run.
- Query index: speeds up list pages and filters.
- Snapshot JSON: useful for compatibility and reproducibility.
- Typed columns: useful for sorting, filtering, charts, and reports.
- Transaction: later, one simulation run should write run/steps/details atomically.

## Migration Strategy

1. Keep existing `fp_simulation_run` working.
2. Add new normalized tables.
3. Add Java writer that stores:
   - run row
   - step rows
   - target truth rows
   - observation rows
   - fused state rows
   - resource assignment rows
   - step metric rows
4. Add read APIs for history detail and chart data.
5. Move Vue playback to read normalized data.
6. Add Agent session persistence after simulation detail persistence is stable.
